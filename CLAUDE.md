## Re-usable components: check, reuse or modify, then build (Jarvis rule)

The shared library is the private repo **baloyinm/Re-usable-Component** (`CATALOG.md` lists everything; `NAMING.md` sets names). Goal: more planning, less work. Nothing is built from scratch if a library component already does the job, or can be modified to do it.

**At the start of every session: library notices**
0. Pull `baloyinm/Re-usable-Component` and read `FIX-NOTICES.md`, `DECISIONS.md` and `WHATS-NEW.md`. For every open fix notice addressed to this project: apply the fix to this project's copy, test it here, then mark the notice done in the library (date, commit) and update this project's line in `USAGE.md`. Follow every decision ("use X, not Y"). Note new components that this project could use.

**Reuse check: required before building anything (every task, every session)**
1. Plan first: list the parts the task needs.
2. Search the library for every part: clone or pull `baloyinm/Re-usable-Component`, run `python3 tools/find.py --plan "<part one>" "<part two>" ...` (it shows the closest components for each part, strong and partial matches), and read `CATALOG.md`. Open the README of every strong or partial match.
3. Decide each part, in this order:
   - **USE**: a component already does the job. Use it as it is.
   - **MODIFY**: a component does part of the job, or would with a new option or setting. Change that component in the library (keep the projects already using it working, raise its version), then use it.
   - **BUILD**: only when nothing comes close, or when changing the closest one would break the projects using it or take more work than building new.
4. Write the reuse check into your plan before writing any code, one line per part: `part · closest component (or none) · USE / MODIFY / BUILD · why`. No building starts until it is written. For every BUILD, say why MODIFY was not possible.
5. Record what you used in the commit: `uses <name> v<version>`, and add or update this project's line in the library's `USAGE.md` (`component · version · project`), so fixes reach you.

**While building**
6. Build every BUILD part, and anything else that could be used again (a screen part, chart, template, script, connector, sync, scheduled-task prompt, business rule), as a self-contained, generic component: settings instead of hard-coded names, amounts or IDs.
6a. **UI and UX are components too (v1.4.0, 10 Nov 2026).** A project with screens must also turn its reusable UI and UX parts (app shell, navigation, forms, tables, cards, status chips, dashboards, empty, loading and error states, theme tokens, phone layouts, print pages, accessibility fixes) into `ui/` components, with `ui/white-label-ui-kit` as the base (improve it, never a parallel kit). Run `ui/ux-audit-script` and `ui/theme-contrast-test` before you publish a screen, and say in the final summary which UI components were used, modified or added.
6a-1. **The UX gate is required (v1.7.0, 11 Nov 2026).** A project with screens carries the `rules/ux-design-rule` block (v1.1.0 or later) in this CLAUDE.md and follows it. Pages are built from the `ui/white-label-ui-kit` page templates and parts (`PageState`, `ErrorSummary`, `SummaryList`, `MoreMenu`, `ConfirmDialog`, `Pagination`, `Breadcrumbs`); a part the kit lacks is added to the kit (MODIFY), never built beside it. No screen is reported done and no `ui/` component is published until the three checks in step 12 of that block pass with zero PROBLEM lines: `ux_audit.py --standard 2 --include-components --strict`, `ux_render_check.mjs --strict` (light and dark) and `ui/theme-contrast-test`. Paste the three result lines in the final summary; a check that could not be run is written NOT RUN, never passed. Old screens that fail are listed in `LIBRARY-LOG.md` under Re-audits and fixed when next touched.
6b. **Demo sign-in (v1.6.0, 11 Nov 2026).** A project with a sign-in and seeded demo users never writes its own demo picker: it USES `ui/demo-quick-login-panel` (server-action cards, or the 1.1.0 persona switcher for demos that only swap a mock session) so evaluators sign in with one click. Accounts and passwords stay on the server or are made up, it is switched on only on the demo deployment, and it is hidden behind `ui/test-tools-gate`. Not a Next.js app: port `src/demo-login.ts`, which is plain logic. A project with no sign-in writes `n/a` in `LIBRARY-LOG.md`.
7. Name it by `NAMING.md`: `<area>/<subject>-<what-it-is>`, for example `ui/hud-donut-chart` or `integrations/markets-price-feed`.

**When it works: commit to the library**
8. MODIFY parts: commit the change to the library as `improve <name> (from <this project>): <what changed>`, raise its version, and update its README and its `CATALOG.md` line. If old use had to break, raise the major version and say in the README what to change. Never make a parallel copy instead.
9. BUILD parts: run the duplicate check again (`python3 tools/find.py <2 to 4 words describing it>`). If anything now does the same job, even partly, treat it as MODIFY. Otherwise add it in its area folder with a `README.md` (header block from `NAMING.md`) and a small `example/`, add one line to `CATALOG.md`, run `python3 tools/find.py --check`, then commit `add <name> (from <this project>)` and push.
10. Two components that do the same job are never allowed. If you find a pair, merge them and mark the weaker one `deprecated`, pointing to the other.
11. Never put passwords, keys, tokens, client data or personal details in the library.
11a. Test before you publish: run the component's example or tests; a component that was not run end to end goes in as `status: draft`.
11b. One publisher at a time. Before any commit to the library, take the publish lock: pull, and if `.publish-lock` exists with an `expires` time still in the future and another holder, wait 5 minutes and check again (up to 6 times), then leave your components for the nightly sweep and say so. Otherwise write `.publish-lock` (`holder: <project> <session>`, `started`, `expires`: started + 60 minutes), commit `lock: <project> publishing` and push. If that push is refused because someone else pushed, pull and check the lock again. Commit your components one at a time (pull --rebase before each push), then delete `.publish-lock`, commit `unlock: <project>` and push. Never delete another holder's lock unless it has expired.
11c. If you cannot publish today, leave a line in this repo's `LIBRARY-TODO.md` (`<date> · <part> · ADD/MODIFY <name> · why`): the nightly library sweep (`automations/library-publish-sweep-prompt`) picks it up, tests it and publishes it.

11d. **Keep the log (v1.5.0, 10 Nov 2026).** Every project keeps `LIBRARY-LOG.md` in its repo root (template: `rules/library-log-template`): one line per library event (ADD, MODIFY or USE) with date, component, version, this project's commit and the library commit, plus a line under Re-audits each time it re-audits its past work. Add the line in the same commit as the change. The library's own matching log is `CONTRIBUTIONS.md`, built by `python3 tools/contrib-log.py --write` before every library commit.

**Workflow operation (v1.15.0, 15 Nov 2026): every user always knows the next step**
W1. Every project with an app where work passes between people (cases, approvals, requests, tickets) follows the `workflow-operation-design` skill (library copy `rules/workflow-operation-rule`) unless the owner says otherwise; apps with no hand-offs are exempt.
W2. Before building, keep `docs/WORKFLOW-MAP.md`: per workflow, each step's role, verb, button(s), time allowed, next step and whether a task is created. A hand-off with no task is a defect; every role in a workflow gets real work, including reviewers (Approve / Send back with reason).
W3. Every role lands on "My work": overdue first, due date and time, a status chip, one primary button that does the step, an "after this" line, and an empty state that says why. Every record shows a next-step banner (who holds it, what, by when). Supervisors get a team view (reassign, complete with reason).
W4. One press completes a step: busy state while saving, idempotent server action, list refreshed from the server, confirmation naming who gets it next and by when. Tasks come from configuration, never typed; never assigned to someone who cannot open the record.
W5. Proof before done: an automated walk of every scenario role by role asserting each hand-off creates exactly one task for the next role; every demo role has open work; a double-press test; a browser walk per role with screenshots. Report the results; a check not run is written NOT RUN.

**At the end of each session**
12. In your final summary, show the reuse check lines and list the components used, modified and added.

**New projects** get this section in their CLAUDE.md on day one, with the shared Jarvis token and model rules.

**Jarvis hub (v1.8.0, 11 Nov 2026): projects report up and take instructions down**
H1. Start of every session: read your inbox file `docs/hub/inbox/<slug>.md` in `baloyinm/jarvis` (slug from `docs/hub/INDEX.md`). Action each `[OPEN]` line, mark it `[DONE I-nnn]` with the date, and report it in your status file.
H2. After each piece of work: append one line to `docs/hub/status/<slug>.md` in `baloyinm/jarvis`: `- date time | DONE/OPEN/BLOCKED/DECISION-NEEDED | what | next | waiting on`. Add the same note to the matching Command Deck action. Nothing is assumed done, nothing goes to other people without Ntsakisi's OK, and no personal data, passwords or keys go in these files. A project that needs another project writes DECISION-NEEDED naming it; Jarvis turns that into an inbox line after his OK.
H3. **Learning note (v1.9.0, 11 Nov 2026).** Ntsakisi wants to learn everything in development from the work. After each piece of work write a learning note into `docs/hub/learn/<slug>.md` in `baloyinm/jarvis`, in the format of `docs/hub/LEARNING-NOTE.md`: the plain-words version (no technical terms) AND the technical version, the problem solved, the idea and why it was chosen over an alternative, how it works step by step, how he can check it, the words explained, and what to learn next. End the status line with `learn: <title>`. Work without a note is not closed.
H4. **First check-in (v1.11.0, 12 Nov 2026).** The first time a project reads this rule (its status file in `baloyinm/jarvis` has no lines yet, or the rule was only just added), do the check-in before other work: apply H1 (read your inbox), then append your first status line to `docs/hub/status/<slug>.md` even if nothing has changed (`- date time | OPEN | first check-in: <where the project stands in one line> | <next step> | <waiting on> | learn: first check-in`), and write a short learning note into `docs/hub/learn/<slug>.md`. A project that cannot push to `baloyinm/jarvis` writes `BLOCKED: no push access to baloyinm/jarvis` in its own `LIBRARY-LOG.md` and says so in its final summary, never silently skips. Jarvis reads these files because it cannot read project repos directly: no status line means it cannot see the project.
**Better-way check (v1.10.0, 11 Nov 2026): protect Ntsakisi from doing things the hard way**
B1. Before acting on any prompt that builds, changes, buys, schedules, deletes or sends something (skip pure questions and small edits), run the `better-way-check` skill: say the goal in one line, then ask five things. Is there a simpler way? Is there a built-in feature, library component or existing tool that already does it? Is it the cheapest in usage and money? Is it safe (security, privacy, hard to undo, goes to other people)? Does it solve the real problem or only the stated one?
B2. If a better way exists, say it FIRST in at most four numbered lines: what he asked, the better way, why, and your recommendation, then ask which he wants. If his way is fine, write one line, "Checked: no better way", and go ahead. Never quietly do it the weaker way, never lecture, never block: it is his decision once he has been told.
B3. Where he was told of a better way and chose his own, record it in one line in the project's status file (`DECISION: chose <his way> over <better way>`) so the choice is not re-argued.
**Next-step recommendations (v1.12.0, 12 Nov 2026): keep every project developing**
N1. After any substantial piece of work (a build, change, review, research, or a reply to comments) and before you stop, end with "Next steps I recommend": at most 3 numbered lines, best first. Each line says what, why it helps, and the cost (which model, roughly how long). Skip it for pure questions and small edits.
N2. Draw them from three places: the work just done (what is half-finished, untested or not verified), the project's open items in its status file and `LIBRARY-LOG.md`, and the library (`WHATS-NEW.md`, the improvement schedule, new components this project could use). Never invent one. If nothing is worth doing, write "No recommendation: nothing open".
N3. Once per session add one line naming the biggest gap in the whole project, not only in this piece of work, then ask one question: which to do first.
N4. Never raise a recommendation he declined again unless something has changed. Record each decline in the project's status file as `DECLINED: <what> (<date>)`. Nothing starts from a recommendation until he says yes, and nothing goes to other people without his OK.
**User guide and documentation (v1.14.0, 14 Nov 2026; one format from v1.19.0, 18 Nov 2026): no app ships without them, and every app uses the same pack**
U1. Every project that has an application (web, phone, desktop, portal, CRM, workflow or admin screens) must have full user documentation unless the owner says otherwise in writing; a project without an application does not need it. Use the `app-user-guide` skill with the library component `rules/user-guide-template` 2.0.0 (the app documentation pack, DNR format): a project never writes its own guide layout, generator or Word build, and never builds a parallel one. A missing part of the pack is added to the component (MODIFY), never built beside it.
U2. The set is the 13 documents of the pack, in `docs/guides/`, built as PDF and DOCX by `pack/build_pack.py` from `pack.json` (the org brand JSON is passed in, nothing hard-coded), `roles.json`, `accounts.json`, `scenarios/*.json`, `known-issues.json` and `content/*.md`: 01 concept; 02 operations guide by role; 03 functional specification with the permissions matrix generated from the real role config; 04 build brief; 05 user test guide; 06 user acceptance test script (Do / Expect / Pass-Fail, per role, sign-off table); 07 quick start; 08 who is who (every user type, can and cannot, which demo person plays them); 09 sign-in (demo cards or made-up demo passwords, local dev accounts, how production sign-in works; never a real password, key or personal detail); 10 end-to-end scenarios from capture to closure for every workflow (sign in as, menu path, data captured, processing, evaluation, decisions, deadlines, documents, money and records, closure, exceptions, flow diagram, one screenshot slot per step, the test that proves it); 11 features guide; 12 administrator guide; 13 not built and known issues. Plus an in-app "User guide" page with downloads.
U3. Written from the running app, never from memory: steps live in the scenario JSON (the pack writes `guide-tasks.json`, `guide-roles.json` and `guide-scenarios.spec.ts` from it), are walked in a browser by `ui/guide-steps-test-runner`, which fills every screenshot slot, and each scenario has that automated end-to-end test. A guide that names a button that does not exist is a defect.
U4. Keep it current: any change to screens, labels, roles, workflows or demo data re-runs the walker and the pack build (`--strict`, zero PROBLEM lines) before release; a feature is not done until its scenario step, screenshot and test exist. Each document shows the release and date it was last checked against (`pack.json` version and date). Paste the pack-report summary line in the final summary; a walk or build that was not run is written NOT RUN, never passed.
U5. Record gaps in `known-issues.json` ("Not built and known issues") rather than describing them; flag legal or statutory points for legal review.
U6. **Every generated document follows the same format (v1.19.0).** Concept, specification, brief, guide, test script, report, minutes, anything a project writes about itself or its users, is built through `email/document-style-kit` from the project's Org settings (D1 to D5), and guides and test scripts only through the pack. A project that already has a one-file `docs/USER-GUIDE.md` keeps it working and moves to the pack the next time it touches its guides (migration notes in the component README).
**Messages to people (v1.16.0, 15 Nov 2026): every email, SMS, WhatsApp, push, in-app, portal message, calendar invite and posted letter has one look and one quality bar**
E1. Every message an app sends to a client or person is built with `email/message-channels-kit` (one Message, rendered to each channel) and the project's Org settings (legal name, registration and VAT numbers, address, contacts, logo, colours; the `messaging` part). No hand-built HTML bodies, no `{{placeholder}}` strings in subjects. Use the message-type templates (notification, task, reminder, approval request, document attached, receipt, security code, welcome, appointment, status update, newsletter); a missing type is added to the kit (MODIFY), never built beside it.
E2. The kit's checkers run in the project's tests and before any send: `assertMessageOk` fails an email without subject, preheader, plain text, legal footer, alt text, Reply-To or (for marketing) unsubscribe, an SMS or WhatsApp message without sender identity and "Reply STOP" where it is marketing, and any message containing an ID number, card number, password, key or unsafe link. Codes EML-, SMS-, WA-, PUSH-, APP-, PTL-, LTR-, ICS-; paste the result line in the final summary.
E3. Marketing needs consent and an opt-out in every channel (unsubscribe link and List-Unsubscribe headers, "Reply STOP", WhatsApp stop button). Codes, security messages and one-time links never go in a subject, a push or an in-app text. Sensitive content goes behind the login, not in the message.
E4. Real sending is switched on only through `integrations/email-sms-messaging` 1.6.0 delivery modes (COMMS_MODE per channel: off, redirect (the default), allowlist, live) wrapped around every sender, with the outbox log and the SWITCH-OVER.md checklist. Nothing reaches a real person until the owner has said yes, mode `live` is set only in production configuration, and the first sends go through `redirect` and `allowlist`.
**Documents (v1.17.0, 15 Nov 2026): every letter, report, invoice, payslip, certificate, form and register has one look and meets one standard (`rules/document-standard-rule`).**
D1. Every generated document (PDF, DOCX, XLSX, print HTML) is built with `email/document-style-kit` from the project's Org settings (`ui/brand-theme-tokens` 1.1.0, one object shared with messages). No name, address, number or colour is written in document code. A document the kit lacks is added to the kit (MODIFY), never built beside it.
D2. Every project keeps `docs/DOCUMENT-INVENTORY.md` (template in `rules/document-standard-rule`): each document it generates, its type code, builder, formats, recipient, personal-information flag, classification and whether the checker runs on it. A document not in the inventory is not sent.
D3. `email/document-standard-checker` runs in the project's tests or CI with `--strict` on the rendered files (and the specs); no push with a PROBLEM line open. A check that could not run is written NOT RUN, never passed.
D4. Legal particulars (tax invoice, credit note, payslip, letter of appointment, lease, company correspondence) follow `business/sa-document-particulars-rule`; lines it flags `verify` are shown to the Information Officer or an attorney before the document goes to a client.
D5. No screenshot PDFs (html2canvas or a page image pasted into a PDF): text must be real text, fonts embedded, tables real tables. Use the kit's PDF or the HTML path with Chrome for a tagged PDF.
S1. Security checks must stay green. Before every push run gitleaks on your tree and the dependency audit (`pip-audit` for requirements files, `npm audit --audit-level=high` for package locks). Never push with a finding open.
S2. Test fixtures must look obviously fake (`test-key-001`, `example-token`), never like a real key (random strings after `key`, `token`, `secret`, `password`). If a scanner still flags a fake value, allow-list that exact literal with a regex in `.gitleaks.toml`, never a whole path. A real secret is rotated and removed, never allowed.
S3. After each push read the Security scan result. If it is red, fixing it comes before any other work; record it in your status file until green. A scan that keeps failing for the same reason is a rule problem: raise it in baloyinm/Re-usable-Component FIX-NOTICES.md.
**Plan first, then watch the pipeline (v1.18.0, 17 Nov 2026): applies to every task in every project, existing and new; run by the `plan-first-pipeline-check` skill; master `rules/plan-first-and-pipeline-rule`**
P1. Before the first edit, command or tool call that builds, changes, deletes, sends or deploys, write a plan card of at most 9 lines: goal, parts, reuse check (part · closest component · USE/MODIFY/BUILD · why), how I will know it works, risk and what needs Ntsakisi's OK, model and agents, better-way check, cost line (estimated build cost in hours and model usage, and the change to monthly running cost). Skipped only for pure questions, one-line edits and read-only research.
P2. Unattended runs write the card as their first log line and carry on; only an irreversible step waits for his OK.
P3. After every push or deploy, read the pipeline result (GitHub Actions, Vercel, Supabase). No result seen means not done.
P4. If it failed: read the failing step's log, fix the cause, push, read again (3 rounds at most, then stop and report). A failure that is not code (billing, missing secret, expired token, quota) is reported with who must act and written as BLOCKED, never guessed at.
P5. One line per red run in the project's status file (`pipeline red: <cause> -> <fix>`). A project with no pipeline gets the minimal one (install, test, build, audit). The final summary shows the plan card, the check results and the run id with its conclusion.
**Know the cost (v1.20.0, 19 Nov 2026): every project knows what it costs to build and run, and the profit; master `rules/cost-to-build-and-run-rule`; run by the `cost-vs-price-model` skill**
C1. Applies to every project with an application that is sold, priced, quoted or costed; internal tools use C5. Every such project keeps `docs/COST-MODEL.md` in its repo: an estimate before building starts, actuals after each release. No project is reported done without it.
C2. Every plan card (P1) carries a cost line: estimated build cost (hours, model usage) and the change to monthly running cost.
C3. Built with the `cost-vs-price-model` skill and the template in `rules/cost-to-build-and-run-rule`; a project sold to clients also gets a spreadsheet calculator (Sheets artifact) with formulas; figures are estimates with source and date. Prices are never changed by the model, only suggested.
C4. Re-run when architecture, cloud prices, plans or prices change, and at least quarterly; one status line per update in the hub status file (`cost model: margin <x>% on <plan/band>`).
C5. Internal tools with no price compare cost to build and run against value (hours saved x rate) and payback.
C6. The user documentation pack (`rules/user-guide-template`) shows the cost and price where the audience needs it: 01 concept and 04 build brief carry the cost-to-build and cost-to-run summary from `docs/COST-MODEL.md`; 05 user test guide and 06 UAT script state the test and demo environments, their made-up data and demo sign-ins, and that their cost is in the model. Client-facing documents show price only, never internal cost or margin. The model also costs, as their own lines in build and run: user documentation (pack, screenshots, Help pages and videos, upkeep), testing (automated, role walks, UAT, browser walks, test environment) and demo and practice use (demo workspace, pilot/sandbox, simulated usage, who pays).
C7. **Projected profit and loss (v1.21.0, 20 Nov 2026).** Every release pack for a project with a price includes an INTERNAL projected profit and loss next to the cost model: scenarios (at least: the first customer only, a small ramp, a full ramp), 3 years (monthly for year 1), subscription and once-off revenue, cost of sales, gross profit, operating costs (development pool, overheads, pilots, travel or "none modelled"), EBITDA, income tax on positive profit only, net profit, cumulative cash and break-even month, with every assumption labelled and editable. Prices and costs come from the pricing source and `docs/COST-MODEL.md`, never invented. Built with `example/pnl_model.py`; never put it in a client document.
**Claude Design first (v1.22.0, 20 Nov 2026): draw it before you build it, where drawing is cheaper than rework; master `rules/claude-design-rule`; run by the `claude-design-first` skill**
G1. Design in Claude Design (the claude.ai artifact types Design and Design System) BEFORE building: a new app, brand or theme (Design System first, once per brand); every new screen or flow; a visible change that moves layout, adds a part or changes a flow step; every marketing or public page. Skip it, with the reason written, for: a bug fix with no visual change, a copy-only change, a cosmetic change that moves nothing (under 30 min of build), an internal admin page built only from kit page templates (R1 to R3, no new part), and documents and messages (their kits own the layout, D1 and E1). Why: a design costs about 2% of the build and finds contrast, target-size and missing-part faults before any code.
G2. A design is not a design without: boards at 1440 and 390 wide, the four states, the brand's Design System in use (nothing invented on the board), at most 10 lines of decisions for the builder, and `ui/theme-contrast-test` run on its tokens. Sonnet designs, Haiku does text and token updates, Opus reviews once (reading only) a new Design System and any R4 or R5 screen, Fable never. Two rounds at most, then build; a third needs Ntsakisi's yes. A new brand's Design System is shown to him before a client sees anything built from it.
G3. One Design System per brand or theme, never a parallel kit: `ui/white-label-ui-kit` is the code and the Design System is its picture, with tokens from the brand object. A part drawn that the kit lacks is a kit MODIFY done before the screen is built.
G4. The plan card (P1) carries one more line when the task touches anything a person sees (the card may be 10 lines with it): `Design: Claude Design <link>` or `Design: skipped because <reason>`. Every screen has a line in `docs/DESIGN-LOG.md`, and `python3 <library>/rules/claude-design-rule/check_design_link.py --base origin/main --strict` runs in the project's tests or CI: a new screen with no linked design is a PROBLEM. Only Ntsakisi waives, in writing (`waived: owner <date>`).
G5. After building: the UX gate plus a side-by-side look (the built screen at 1440 and 390 next to its board; each difference fixed or written down). The final summary carries one line: `Design: <link> · rounds <n> · side-by-side <done / NOT RUN> · check <result line>`.
